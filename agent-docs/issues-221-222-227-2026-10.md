Changes prepared for `1.6.5.3-cpr-vcodex` on 15 October 2026, based on
`1.6.5.2` (`5d469e2b`, branch `integration/crosspoint-2026-10-07`).
The release contains fixes for demonstrated code paths; the original reports
are not all reproducible on the available host simulator.

## Recovery boundaries

- Recovery is eligible only when the explicit memory preflight rejects the
  current operation before any HTTP request has been performed. Client
  initialization errors, TLS failures and uncertain registration responses do
  not authorize a replay through this path.
- A small, versioned and checksummed RTC record references the existing saved
  profile. It adds no password or password-hash copy. Boot consumes the record
  before starting work, validates the profile identity, and prevents a second
  recovery restart from the resumed activity.
- Authentication and manual sync require the same active profile. Registration
  can resume the separately selected saved profile without activating it.
- Manual sync requires a pending reader handoff and a successful state save.
  It preserves the book and local reading position. Automatic sync and already
  completed outcomes are excluded.
- Recovery, panic and Back-button boot routes retain their priority. Reader
  fonts are loaded again when normal reading resumes.
- TLS certificate verification, memory thresholds, request timeouts and
  existing retry limits remain enabled. Error diagnostics omit URL credentials,
  paths and query parameters. Empty server URLs still resolve to
  `https://sync.koreader.rocks:443`.

1. On X3/X4, repeat registration, authentication and manual sync after reading
   with an SD font. Confirm that a rejected memory preflight can recover once,
   reconnect and finish, then return to the same book position and font.
2. If memory is still insufficient after the restart, confirm that the reader
   displays the failure rather than repeatedly restarting. Capture the exact
   error and server URL without sharing passwords.
3. Try a separately selected registration profile and verify the active profile
   remains unchanged. For manual sync, check both download and upload choices.
4. Open the affected large Highlights list, use short presses and held buttons,
   and confirm the selected row stays visible. Reproduce the older-highlight
   error separately with its exact action and outcome.

change partition tables, bootloaders or update paths. End-to-end OTA/SD testing
and the earlier locked-X3 and SD-mounting reports remain separate. X4 Pro
distribution remains withdrawn.

## Legacy Highlights follow-up — prepared for 1.6.5.4 (16 October 2026)

The reporter confirmed that the Highlights list is responsive in `1.6.5.3`.
[The follow-up photos and description](https://github.com/franssjz/cpr-vcodex/issues/227#issuecomment-6205421666)
show intact saved Korean text, but older highlights open the preceding page,
lose their shading, or shade an earlier sentence. Highlights recreated since
`1.6.5.1` remain correct. This clarifies the older-highlight uncertainty above;
the reporter's original EPUB and `bookmarks.bin` are still needed for validation.

The stored visible-text anchor identifies the old page start, not the selected
phrase. A layout/tokenization change can invalidate both that page and its word
indices. Older Korean snippets can also contain spaces between individual
syllables, while the current renderer groups them into words. Previously, a
failed text match could fall back to those stale indices and shade unrelated
words. A synthetic Korean EPUB reproduces both the wrong jump and wrong shading
with the previous code.

The correction prepared for `1.6.5.4-cpr-vcodex` carries the selected bookmark
identity through both the reader and global Highlights lists. On activation,
it searches for the complete saved text within three pages of the resolved
page hint, allowing a match to
continue onto the following page. Matching tolerates legacy CJK token spacing
and current inserted hyphens, while retaining Latin word boundaries and literal
saved hyphens. It requires whole-word endpoints and a unique match across that
window; missing, partial and ambiguous matches never use stale word indices.

Recovery keeps at most two loaded pages and eight numeric resolutions for the
current section/layout. If a partial cache does not yet cover the complete
search window, recovery stops safely; reopening the highlight retries after
normal background pagination advances. It does not synchronously replay a
partial chapter just to recover a highlight, and feeds the watchdog while scanning.
No nearby-page reads occur in highlight paint passes, and matching does not
allocate normalized text or truncate the page to a fixed word-array length.
Deleting bookmarks or changing the section/layout invalidates the cached ranges.
The original `bookmarks.bin` records are not migrated or rewritten by recovery.
Fresh selections retain their exact current range even for repeated text,
truncated snippets or selected hyphen fragments, provided the selector's visual
word order agrees with the page's traversal. That trust expires with the current
layout/cache; loaded records always undergo the conservative text check.

The full native suite passes **735/735** tests, including 21 matcher cases and
11 bookmark-window cases. Logs are
`artifacts/issue-227-legacy-native-{build,tests}.log`.

`test/simulator/highlights_legacy.py` covers eight legacy scenarios: shifted v4
records in both directions, a stale v5 page-start anchor, same-page wrong word
indices, missing text, repeated/ambiguous text, the global Highlights route,
and both halves of a phrase across a page boundary. The corrected screenshots
match the reference pages exactly and all original bookmark files remain
byte-for-byte unchanged. A ninth case creates a repeated-word highlight through
the normal UI and verifies its saved record, immediate shading and list reopen.
It allows only up to 25 pixels on the reference highlight's rightmost column;
every other pixel is exact, and the saved/reopened images must be identical.
The previous implementation fails the relevant legacy cases, and the version
without the fresh-selection cache fails the ninth case with missing interior
shading. The final fresh-selection run uses the exact final reader source.

Simulator evidence is under
`artifacts/highlights-legacy/highlights-legacy-mvbg2qs2/` (legacy matrix) and
`artifacts/highlights-legacy/highlights-legacy-iv478w4o/` (final fresh selection).
`artifacts/highlights-legacy/validation-final.json` combines the nine results,
source provenance and unchanged-file hashes.
The final ESP32-C3 `default` build also passes; its packaged image is
6,362,928 bytes, within the 6,553,600-byte X4 OTA slot. The build log is
`artifacts/issue-227-legacy-default-build.log`.
The `gh_release` dry run passes with a 6,285,184-byte image (268,416 bytes
below that slot) and 62,072 bytes of static RAM. The firmware budget gate
passes. Logs and reports are `artifacts/issue-227-legacy-release-build.log`
and `artifacts/issue-227-legacy-firmware-budget.{json,md}`. Its local candidate
version is `1.6.5.4`; `VCODEX_RELEASE_DRY_RUN=1` left the release counter
unchanged. This validation run did not publish a tag, GitHub release or Pages
update; the release workflow supplies the final published binary and metadata.

This deliberately bounded recovery does not promise to locate text more than
three pages away, a phrase spanning more than two current pages, an endpoint now
inside a larger word, or a repeated phrase that cannot be distinguished safely.
Physical-device memory/timing checks and validation against the reporter's
original files remain outstanding. This follow-up is not included in the
already-published `1.6.5.3` release.
